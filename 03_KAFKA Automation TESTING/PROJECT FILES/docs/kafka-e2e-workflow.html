2How we solved it

To test a producer and a consumer we needed both to exist. So the solution builds a small, realistic order-processing system in Node-RED, runs it against a real Kafka broker in Docker, and then tests it manually and automatically.

  1. Created a reproducible environment. docker-compose.yml starts a single-node Kafka broker (KRaft mode, no ZooKeeper), a one-shot kafka-init job that creates the three topics (auto-create is disabled, so typos fail loudly), and a Node-RED container. One command brings it all up and waits until each service is healthy.
  2. Built the system under test in Node-RED. The Order producer tab exposes POST /orders, validates the order, wraps it in an OrderCreated event and publishes it to Kafka. The Order consumer tab reads those events, computes totals, and writes an OrderProcessed result, or an OrderRejected record to a dead-letter topic when the input is bad.
  3. Defined a single event contract. node-red/lib/order-event.js holds the validation rules, the event envelope and the result calculation. Both flows use it, and it also has its own unit tests.
  4. Wrote 6 scenarios, in Gherkin and as manual test cases, that cover the happy path, validation, broker outage, malformed messages and consumer restart. Each has preconditions, test data, steps and exact expected results, and each was executed and its observed results recorded.
  5. Automated one producer and one consumer scenario twice: as Gherkin scenarios run by Cucumber with Chai step definitions, and as plain Mocha + Chai specs. Both share the same client objects. Each test uses an independent kafkajs client as the oracle, so the test never trusts the system under test to grade itself.
  6. Made the tests reliable. Each run has a unique ID and its own consumer group. Subscribers are confirmed ready before anything is published, every wait is bounded with a clear failure message, and every client is cleaned up afterwards.
  7. Added quality gates. The project has ESLint and Prettier, unit tests for the contract, and a GitHub Actions pipeline (ci/github-actions-e2e.yml) that runs lint, the unit tests and the full integration suite.

Key design decisions

Decision Why
Node-RED function nodes using kafkajs, not a palette Kafka node The community Kafka nodes differ in their retry, commit and shutdown behaviour. A known client makes every expected result exact and reviewable, with only one dependency.
The offset is committed only after the result or DLQ write succeeds Gives at-least-once delivery: a crash can never silently skip a record.
Bad messages go to a dead-letter topic One poison message cannot block the partition, and the consumer moves on to the next record.
Expected values are literals in the tests totalAmount: 71.8 is written out by hand rather than recomputed with the code under test, so a bug in the calculation cannot hide itself.
Real broker, not a mock Partitions, offsets, consumer groups and acks are real, which is what Kafka testing is actually about.

3Architecture and event contract

Components

Component Details
Kafka broker apache/kafka:3.9.1, KRaft single node. Host listener localhost:9092 (tests), internal listener kafka:19092 (Node-RED).
kafka-init One-shot job that creates qa.orders.v1, qa.orders.processed.v1 and qa.orders.dlq.v1 (1 partition each), then exits.
Node-RED Node-RED 4.0.9 image with kafkajs@2.2.4. Two tabs: Order producer and Order consumer.
Consumer group nodered-order-processor; commits after every record, only once the output write has succeeded.
Producer retries PRODUCER_RETRIES=2, 300 ms initial backoff, 1 s connect timeout. When the broker is down the client gets a 503 in about 1–2 s.

Event contract: OrderCreated v1

Record key = orderId. Headers: correlation-id, event-type, schema-version. 

{
  "schemaVersion": 1,                    // added by the producer
  "eventType": "OrderCreated",           // added by the producer
  "eventId": "6f1c…",                    // UUID, added by the producer
  "correlationId": "it-producer-1731…",  // X-Correlation-Id header, else generated
  "occurredAt": "2026-11-12T22:22:33.000Z",
  "orderId": "ORD-1",                    // required
  "customerId": "CUST-1001",             // required
  "currency": "USD",                     // required, ^[A-Z]{3}$
  "items": [ { "sku": "SKU-1", "quantity": 2, "unitPrice": 9.99 } ]  // required, non-empty
}

The consumer turns a valid event into OrderProcessed, with itemCount (the sum of the quantities), totalAmount (the sum of quantity × unitPrice, to 2 decimal places), status: "PROCESSED", sourceEventId and source {topic, partition, offset}. Invalid JSON or a schema violation becomes OrderRejected on the DLQ, with reason: INVALID_JSON | SCHEMA_VALIDATION_FAILED.

4End-to-end workflow

The path of one order

  1. Request. The client sends POST /orders with orderId, customerId, currency and items. The correlation ID comes from the X-Correlation-Id header, then body.correlationId, otherwise a new UUID.
  2. Validate. If a field is missing or invalid, the producer returns 400 VALIDATION_FAILED with details and publishes nothing.
  3. Publish. The producer wraps the order in the OrderCreated envelope and sends it with key = orderId and acks=all. When the broker acknowledges, the client gets 202 PUBLISHED with the partition and offset. If the broker is unreachable after the retries, the client gets 503 BROKER_UNAVAILABLE and nothing is buffered.
  4. Consume. The long-lived Node-RED consumer reads qa.orders.v1 in group nodered-order-processor.
  5. Process. A valid event produces OrderProcessed on the processed topic. Bad JSON or a schema violation produces OrderRejected on the DLQ, and the consumer continues with the next record.
  6. Commit. The offset is committed only after the step 5 write succeeds (at-least-once). A restart with the same group ID resumes from the committed offset.

Full run from start to shutdown

docker compose up -d --build --wait
   ├─ kafka starts (KRaft) → healthcheck passes
   ├─ kafka-init creates the 3 topics → exits 0
   └─ node-red starts → producer ready, consumer joins its group
npm ci
npm run test:unit   # 15 contract tests, no broker needed
npm test            # KAFKA-P-01 + KAFKA-C-01 against the real stack
   ├─ 2 passing → optionally run the manual scenarios
   └─ failure   → docker compose logs node-red / kafka (the failure message names what was missing)
docker compose down -v   # removes containers, network and broker data

5Manual test scenarios

The six scenarios are below; expand one to see its steps and expected results. The full versions, with copy-paste shell helpers, are in docs/manual-test-scenarios.md. Every scenario was executed against the Docker stack, and each one's observed result matched its expected result.

Producer

KAFKA-P-01 · Producer publishes a valid event Automated Pass

Preconditions: stack running, Kafka healthy, Node-RED reachable on :1880.

Steps: note the end offset of qa.orders.v1; POST /orders with a valid body and X-Correlation-Id: manual-p01; read the topic.

Expected:

  • HTTP 202 {"status":"PUBLISHED", topic, partition, offset, key:"ORD-P01", eventId, correlationId}, with the offset equal to the previous end offset.
  • Exactly one record at that offset, key ORD-P01, headers correlation-id, event-type: OrderCreated, schema-version: 1.
  • The payload has the envelope fields and the business fields exactly as sent; the end offset grew by 1.
KAFKA-P-02 · Producer rejects an event missing a required field Manual Pass

Steps: POST a body without customerId, then repeat for orderId, currency, items and "items": [].

Expected:

  • HTTP 400 {"status":"REJECTED","error":"VALIDATION_FAILED","details":["customerId is required"]}.
  • The end offset is unchanged and nothing is published; Node-RED logs a REJECTED warning.
  • Each variant names its field; an empty array gives items must be a non-empty array.

Observed: 400 with the expected details; end offset 31 before and after.

KAFKA-P-03 · Producer handles an unavailable broker Manual Pass

Steps: docker compose stop kafka; POST an order and time it; check that Node-RED is still up; docker compose start kafka; POST again.

Expected:

  • 503 BROKER_UNAVAILABLE within 5 s, with retries: 2; the request does not hang.
  • The Node-RED container keeps running.
  • After recovery the next request returns 202 without restarting Node-RED, and only the post-recovery message is on the topic (no replay).

Observed: 503 in 0.8–2.0 s; the next request after recovery returned 202.

Consumer

KAFKA-C-01 · Consumer processes a valid event and produces a downstream result Automated Pass

Preconditions: group nodered-order-processor is Stable with 1 member.

Steps: publish a valid OrderCreated (key ORD-C01, items 1 × 49.90 + 3 × 7.30) directly to qa.orders.v1; read the processed topic; check the group lag.

Expected:

  • One OrderProcessed with key ORD-C01, itemCount: 4, totalAmount: 71.8, and sourceEventId and source pointing to the input record.
  • Nothing on the DLQ; group lag 0.
KAFKA-C-02 · Consumer handles a malformed event and continues Manual Pass

Steps: publish one invalid-JSON record followed by a valid one; read the DLQ and processed topics; repeat with valid JSON that breaks the schema.

Expected:

  • DLQ: OrderRejected with reason: INVALID_JSON, the source offset and the original rawValue.
  • The next valid record is processed at offset + 1 (totalAmount: 20); the bad record does not block the consumer.
  • Lag 0, so the bad record is committed and not retried forever. The schema variant gives SCHEMA_VALIDATION_FAILED with 6 listed errors.

Observed: bad record at offset 26 went to the DLQ, offset 27 was processed, lag 0.

KAFKA-C-03 · Consumer restarts and resumes from its committed offset Manual Pass

Steps: note the committed offset C; docker compose stop node-red; publish 2 events; check the lag; start Node-RED with the same group ID; check again.

Expected:

  • While stopped: the group has no active members, and lag = 2 (current C, log end C+2).
  • After restart: lag 0 with a new consumer ID in the same group.
  • Both new events are processed exactly once, in order; nothing before C is reprocessed.

Observed: committed 32, lag 2 → committed 34, lag 0, with no reprocessing.

How a Gherkin step becomes a Kafka check

Each step maps to a step definition through a Cucumber expression. Step definitions stay thin: they call the same client objects, builder and config the Mocha specs use, and assert with Chai. 

// features/step_definitions/consumer.steps.js
Then('the OrderProcessed result has:', function (table) {
  // Expected values are literals in the feature file, never recomputed with the code under test.
  const result = this.record.json;
  expect(result.eventType).to.equal('OrderProcessed');
  for (const { field, value } of table.hashes()) {
    expect(result[field], field).to.deep.equal(parseValue(value));
  }
});
Background
Checks the broker, topics and Node-RED are reachable, failing with a "start the stack" hint if not, then creates the run id.
World
A fresh KafkaOrdersWorld per scenario holds the run id, clients and matched record, so scenarios never share state.
Hooks
The After hook closes every client and deletes test consumer groups; on failure it attaches the response and record to the report.
Readable tables
Topics are named by alias ("orders", "processed"); {runId} in a cell becomes the run's correlation id.

Producer test flow (KAFKA-P-01)

  1. Start a test subscriber on qa.orders.v1: record the end offsets, join a run-unique group, and seek to the recorded offsets so it is ready before anything is published.
  2. NodeRedOrdersClient.createOrder(order, { correlationId: runId }) → Node-RED publishes the event.
  3. subscriber.waitFor(correlationId === runId), bounded at 15 s.
  4. Assert the HTTP 202 ack, topic, key, that the partition and offset match the ack, the headers, the exact payload key set, a UUID eventId, an ISO timestamp, the items passed through unchanged, and exactly one record.
  5. after: disconnect and delete the test consumer group.

Consumer test flow (KAFKA-C-01)

  1. waitForGroupStable('nodered-order-processor'): the system under test must be subscribed first.
  2. Start a test subscriber on qa.orders.processed.v1.
  3. KafkaTestPublisher.publishOrderCreated(anOrder()…buildEvent()) straight to Kafka (bypassing Node-RED).
  4. Wait for the OrderProcessed result with this run's correlation ID.
  5. Assert the key, headers, itemCount: 4, totalAmount: 71.8, that source equals the published offset, and exactly one result.

Reliability techniques

Unique per run
Each run generates a runId that is used as the correlation ID, inside the order ID, and in the consumer group name, so runs never interfere with each other.
Ready before publish
Subscribers seek to pre-recorded end offsets after joining their group, so no message can be missed.
Bounded waits
No sleep(). Every wait has a timeout and a failure message that names what was missing.
Clean teardown
All clients are closed and test groups are deleted. Mocha runs without --exit, so a leaked client would make the run hang.

9How to run

Prerequisites

  • Docker Desktop (or Docker Engine) with Compose v2, and the engine running
  • Node.js 18.18 or newer (Node 20 or 22 LTS recommended)
  • Free ports 9092 (Kafka) and 1880 (Node-RED)

Steps

# 0. Go to the project folder
cd "03_KAFKA Automation TESTING/PROJECT FILES"

# 1. Start Kafka, create the topics, start Node-RED (waits until everything is healthy)
docker compose up -d --build --wait

# 2. Install the test dependencies (cucumber, mocha, chai, kafkajs, eslint, prettier)
npm ci

# 3. Run the tests
npm test                  # everything: Gherkin features, then Mocha specs
npm run test:bdd          # Gherkin features only → reports/cucumber-report.html
npm run test:bdd:producer # Gherkin KAFKA-P-01
npm run test:bdd:consumer # Gherkin KAFKA-C-01
npm run test:mocha        # Mocha + Chai specs for the same two scenarios
npm run test:unit         # 15 contract unit tests (no broker needed)
npm run test:bdd:dry      # every automated Gherkin step has a definition (no broker)
npm run lint              # ESLint + Prettier check

# 4. Shut down and remove containers, network and broker data
docker compose down -v

Useful while testing

docker compose ps                          # container health
docker compose logs -f node-red            # debug output and warnings from the flows
docker compose restart node-red            # consumer restart (KAFKA-C-03)
docker compose stop kafka / start kafka    # broker outage (KAFKA-P-03)
# Node-RED editor: http://localhost:1880

Environment overrides: KAFKA_BROKERS (default localhost:9092), NODE_RED_URL (default http://localhost:1880), TEST_WAIT_MS (default 15000).

11Known limitations

  • A single broker and single-partition topics, by design, to keep the setup small and reproducible.
  • At-least-once delivery: a crash between the result write and the offset commit can produce a duplicate result.
  • A body that is not JSON is rejected by Node-RED's HTTP body parser (400, HTML) before the flow runs.
  • Four scenarios (P-02, P-03, C-02, C-03) are tagged @manual. Their Gherkin is complete, so automating one means adding step definitions and removing the tag. The code-structure guide in docs/e2e-workflow-and-code-structure.md has a worked recipe for automating C-02 next.

On Node 18.12 the run prints a harmless ExperimentalWarning: The Fetch API is an experimental feature. Node 18.18+ (or 20/22 LTS) is the supported version and removes the warning.
