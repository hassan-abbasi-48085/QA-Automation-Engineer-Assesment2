1Problem statement

Task 2: UI Automation testing.

Choose any webpage of your choice.

2How we solved it

  1. Picked a stable, public targetThe practice login page publishes its own demo credentials (student / Password123) and has fixed error messages. That makes results repeatable and means no private data is involved.
  2. Explored the page manuallyWe noted the field labels, the button name, the redirect URL after login, and how the error banner appears. TC-LOGIN-01 to 03 were first run by hand on 2026-11-12.
  3. Wrote the manual test casesThere are 3 required scenarios plus 5 more: positive, negative, UI/security, logout and recovery. Each has an ID so it can be traced through to the automation.
  4. Wrote the same cases in GherkinOne .feature file holds all 8 scenarios in plain Given / When / Then, with the test data written into the steps. It is readable by non-developers and is the file the automation actually runs.
  5. Chose Playwright + playwright-bddplaywright-bdd turns the Gherkin into Playwright tests. That keeps Playwright’s auto-waiting, assertions that retry on their own, parallel workers, traces and HTML reports, and adds a Cucumber report.
  6. Built the layers: page objects, then fixtures, then stepsLocators and page actions live in pages/. The page objects are passed to each scenario as Playwright fixtures, and the step definitions are thin wrappers that call them.
  7. Handled the one tricky elementThe error banner #error is always in the page, hidden only with opacity: 0, and already says “Your username is invalid!” before you click Submit. A plain visibility check would pass falsely, so the page object waits for the show class before checking the text.
  8. Ran it against the live site and checked it can failSee section 7.

Step definitions: steps/login.steps.js (excerpt)

Given('I open the login page', async ({ loginPage }) => {
  await loginPage.goto();
});

When('I log in with username {string} and password {string}',
  async ({ loginPage }, username, password) => {
    await loginPage.login(username, password);
  });

Then('I am logged in as {string}', async ({ loggedInPage }, username) => {
  await loggedInPage.expectLoaded(username);
});

Then('I see the error message {string}', async ({ loginPage }, message) => {
  await loginPage.expectError(message);
});

Then('I am still on the login page', async ({ loginPage, loggedInPage }) => {
  await loginPage.expectOnLoginPage();
  await loggedInPage.expectNotLoggedIn();
});

Then('the password field is masked', async ({ loginPage }) => {
  await loginPage.expectPasswordMasked();
});
// … plus: I have logged in / I have failed to log in / I type … into the password field /
//         I log out / the password field holds the value / back on the login page

Every step is a page-object method call. The step file contains no locators, selectors or expect() calls.

Page object: pages/LoginPage.js

class LoginPage {
  constructor(page) {
    this.page = page;
    this.path = '/practice-test-login/';
    this.usernameInput = page.getByLabel('Username');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton  = page.getByRole('button', { name: 'Submit' });
    // #error is always in the DOM (opacity 0); the site reveals it by adding the "show" class.
    this.errorMessage  = page.locator('#error');
  }

  async goto() {
    await this.page.goto(this.path);
    await expect(this.submitButton).toBeVisible();
  }

  async login(username, password) {
    await this.usernameInput.fill(username);
    await this.passwordInput.fill(password);
    await this.submitButton.click();
  }

  async typePassword(password) { await this.passwordInput.fill(password); }

  // ---------- Assertions ----------
  async expectError(text) {
    await this.expectAnyError();
    await expect(this.errorMessage).toHaveText(text);
  }

  async expectAnyError() {
    await expect(this.errorMessage).toHaveClass(/\bshow\b/);
  }

  async expectPasswordMasked()       { await expect(this.passwordInput).toHaveAttribute('type', 'password'); }
  async expectPasswordValue(value)   { await expect(this.passwordInput).toHaveValue(value); }
  async expectLoginFormShown()       { /* username, password and Submit visible */ }

  async expectOnLoginPage() {
    await expect(this.page).toHaveURL(/\/practice-test-login\/?$/);
    await expect(this.submitButton).toBeVisible();
  }
}

LoggedInPage.js follows the same pattern. It has a heading, a welcome-text locator and the Log out link. expectLoaded(username) checks the URL, heading, welcome text and Log out link. expectNotLoggedIn() checks that the Log out link is absent, and logout() clicks Log out. Both page objects group their code into Locators, Actions and Assertions, and declare parameter types in JSDoc, so // @ts-check passes with no errors.

6How to run

Prerequisites

  • Node.js 20 or later, and npm. Both Playwright 1.62+ and playwright-bdd 9 need it, and package.json declares "engines": { "node": ">=20" }.
  • Internet access to practicetestautomation.com.

Install (once)

# PowerShell (Windows)
cd "C:\Users\a_hos\Downloads\00_Assignment V2\00_Assignment\02_LOGIN TEST\Project Files"
# Git Bash: cd "/c/Users/a_hos/Downloads/00_Assignment V2/00_Assignment/02_LOGIN TEST/Project Files"
npm ci
npx playwright install chromium
# Linux / CI image: also install the browser's OS libraries
npx playwright install --with-deps chromium

Run

npm test                                                 # bddgen + all 8 scenarios, headless
npm run test:smoke                                       # @smoke only (TC-LOGIN-01, the primary scenario)
npx bddgen --tags "@TC-LOGIN-02" && npx playwright test   # one scenario by ID tag
npx bddgen --tags "@negative" && npx playwright test      # a group by tag
npm run test:headed                                      # watch the browser
npm run report                                           # open the Playwright HTML report

Why bddgen first? Playwright runs the generated files in .features-gen/, not the .feature file directly. bddgen regenerates them and fails fast if any Gherkin step has no matching definition. The npm scripts always run it first.

Where the output goes

  • Console: the list reporter prints one line per scenario, including its tags.
  • playwright-report/index.html: the Playwright HTML report, with each Gherkin step shown as a test step.
  • cucumber-report/index.html: a Cucumber-style report of features, scenarios and steps.
  • test-results/: a trace and screenshot for each failed scenario only. Open a trace with npx playwright show-trace <file>.zip.

8Best practices applied

PracticeHow it shows up here
BDD with GherkinTest cases are written as behaviour, in business language. The .feature file is both the living specification and what the automation runs.
Traceability by tagsEvery scenario, including each Outline row, carries @TC-LOGIN-0x matching the manual case. Group tags (@smoke, @negative, …) select subsets.
Scenario Outline for data variationsThe four rejected-login cases share one set of steps, with the data in Examples tables.
Reusable, declarative stepsOne step with parameters (I log in with username {string} and password {string}) is used by seven scenarios. Given sets up state, When acts, Then asserts.
Page Object ModelStep definitions only call page-object methods, with no locators, selectors or expect(). Locators and assertions live once in pages/, grouped into Locators, Actions and Assertions.
Fixtures, not globalsPage objects are injected as Playwright fixtures, so each scenario gets fresh instances. Scenarios are independent and run in parallel.
User-facing locatorsgetByLabel and getByRole. The error banner has no accessible role, so it uses its stable #error id.
Assertions that retry, no sleepstoHaveURL, toBeVisible, toHaveClass, toHaveText, toHaveAttribute, toHaveCount. There is no waitForTimeout.
Correct check for the hidden errorWaits for the show class before checking the text, which avoids a false pass on an element that is in the page but transparent.
Proven able to failA deliberately wrong expected value was confirmed to fail with a clear diff.
Reporting and debuggingConsole, Playwright HTML and Cucumber HTML reports. Trace and screenshot are kept for failed scenarios only.
CI-ready, reproducibleforbidOnly and one retry when CI is set. Exact versions are pinned with a committed lockfile and a Node engine constraint. Generated and report folders are git-ignored.
