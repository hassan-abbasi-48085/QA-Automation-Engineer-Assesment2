1Problem statement

Task 1: Automate API testing.

Write an automation test using Postman or any tool of your choice.

Endpoint: https://gorest.co.in/
Resource: POST /public/v2/users

Run an HTTP POST on the above endpoint. Create a new user and assert that you can find the newly created user in the Get user endpoint (https://gorest.co.in/public/v2/users/7014306).

Assert the presence of the various properties in the returned object.

Put another way, the test has three jobs:

  • Create a user with POST /public/v2/users.
  • Get that same user back with GET /public/v2/users/{id}. The ID 7014306 in the task is only an example. The test uses the ID returned by its own POST.
  • Check that the returned object has the expected properties and values.

Core workflow (Task 1)

  1. Check credentials. The Background step reads GOREST_TOKEN. If it is missing, the scenario fails right away with a clear "Missing credentials" message.
  2. Build a unique payload. A synthetic name, a unique email made from a timestamp plus a random number, a valid gender (male or female) and a valid status (active or inactive).
  3. POST /users. Assert HTTP 201, check that the response id is a positive integer, and capture it.
  4. GET /users/{id} with the captured ID. Assert HTTP 200.
  5. Check the properties. The object must contain id, name, email, gender, status. The id must equal the created ID, and the other four fields must equal the values that were sent.
  6. Clean up. An After hook deletes every user the scenario created. If the scenario already failed, cleanup errors only print a warning, so the original failure stays the reported cause.

Beyond the required task

The extended suite adds negative, validation, lifecycle and credential scenarios so the endpoint is covered more fully:

  • Authentication: POST with no token and with an invalid token both return 401.
  • Validation: a duplicate email, a bad email format, an invalid gender, an invalid status and an empty body each return 422, with an error for the correct field. The three single-field cases share one Scenario Outline with an Examples table.
  • Lifecycle: the response is JSON with exactly the 5 keys, PATCH updates are visible through GET, and DELETE returns 204 followed by 404 on GET and on a second DELETE.
  • Credentials: an unset or whitespace-only token fails before any request is sent. These run offline.

The required test: features/01-create-and-get.feature

@task1 @smoke @requires-token
Feature: Create a user and retrieve it by ID

  Background:
    Given the base URL is "https://gorest.co.in/public/v2"
    And a valid bearer token is read from the "GOREST_TOKEN" environment variable
    And a user payload with a unique name and email, a valid gender and a valid status

  Scenario: POST /users creates a user and returns HTTP 201 with an ID
    When I send a POST request to "/users" with the user payload
    Then the response status should be 201
    And the response body should be a JSON object
    And the response "id" should be a positive integer
    And I store the response "id" as the created user ID
    And the created user is tracked for cleanup

  Scenario: GET /users/{id} returns HTTP 200 and the submitted values
    Given a user was created with the user payload
    When I send a GET request to "/users/{created user ID}"
    Then the response status should be 200
    And the response body should contain the keys:
      | id | name | email | gender | status |   (one key per row in the file)
    And the response "id" should equal the created user ID
    And the response fields should match the submitted payload:
      | name | email | gender | status |

Matching step definitions (excerpt)

When('I send a POST request to {string} with the user payload', async function (path) {
  const res = await this.send('POST', path, { body: this.payload });
  this.track(res.body);                      // the After hook deletes it
});

Then('the response status should be {int}', function (status) {
  expect(this.response.status, api.describeResponse('Last request', this.response)).to.equal(status);
});

Then('the response body should contain the keys:', function (table) {
  expect(this.response.body).to.be.an('object').that.includes.all.keys(...columnValues(table));
});

Then('the response fields should match the submitted payload:', function (table) {
  for (const field of columnValues(table)) {
    expect(this.response.body[field], field).to.equal(this.payload[field]);
  }
});

Request flow

cucumber-js ──► new GoRestWorld()               (fresh state for each scenario)
  │
  ├─► Background: read GOREST_TOKEN               (fail fast if missing)
  │
  ├─► POST /public/v2/users   {name, email, gender, status}
  │      ◄── 201 {id, ...}    → store id, track it for cleanup
  │
  ├─► GET  /public/v2/users/{id}
  │      ◄── 200 {id, name, email, gender, status} → assert keys and values
  │
  └─► After hook: DELETE /public/v2/users/{id}   (204 or 404 both count as clean)

4How to run

You need: Node.js 18 or newer (Node 20+ removes the "Fetch API is experimental" warning) and a GoREST access token from https://gorest.co.in/consumer/login.

PowerShell (Windows)

cd "C:\Users\asifu\Documents\00_Assignment\01_GO REST\qa-assessment-task1-extended"
npm install
$env:GOREST_TOKEN = "<your-gorest-token>"
npm test
Remove-Item Env:GOREST_TOKEN

Bash (Git Bash, macOS, Linux)

cd "/c/Users/asifu/Documents/00_Assignment/01_GO REST/qa-assessment-task1-extended"
npm install
read -rsp "GoREST token: " GOREST_TOKEN && echo && export GOREST_TOKEN
npm test
